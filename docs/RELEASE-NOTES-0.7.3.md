# Flower MCP 0.7.3

An open PVP now clearly holds affected repository execution while engineering
investigation and ordinary plan preparation continue within confirmed intent.
The recipe and exported Markdown explain how to complete ownership, verification
intent and producer/consumer declarations. A draft remains nonexecutable;
new gaps found offline are retained as observations/proposals for ordinary
accepted mutations on reconnection. No PVP or human approval gate is waived.

Exact `replace_plan` and `revise_unit` help includes concrete examples and the
relationship among `implements`, `unit_checks` and `verifies`. A local check needs
an exact same-unit `kind=unit_check` verification statement; criterion prose is
separate; selecting which active criterion a check verifies requires engineering
investigation. Stable criterion numbers are unchanged. Array patches replace whole
arrays. Use current returned revisions, review/accept the new proposed plan and
revalidate before execution.

Read-only validation/TODO responses add a bounded `next_gate.repair` descriptor
for known declaration gaps, preserving the original PVP and primary read route.
It names current known identities, CAS and exact authoring help, but remains
`ready_to_call=false` with no generated patch, criterion mapping, actor or request.
Ambiguous producer/consumer repairs remain explicit engineering choices.
See [plan authoring](PLAN-AUTHORING.md).

`revise_unit` failures now use the existing structured mutation guard and retain
original request correlation. Ancillary lifecycle repair may already have run:
failed mutation effects remain `unknown`, without a fabricated no-effect receipt.
A blocked PVP read remains an observation. Updating code never replays work or
rewrites uncertain historical responses.

environment, profile, SQLite database, YAML and client configuration. The installer

and installer behavior are unchanged. No data migration or project reset is needed.

public MCP checks cover incomplete plans, read-only hints, strict draft export,
explicit targeted repair, proposed-plan acceptance and stale CAS errors. Existing
Release CI gates exact packages. Real client adoption belongs to its owner;
no new upgrade campaign, model benchmark result, U6 or human acceptance is claimed.
